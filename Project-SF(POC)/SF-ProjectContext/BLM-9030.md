# Feature Context: BLM-9030 Unified Validation Framework for Opportunity Fields Required During Bid Creation and Later Stages

## Overview
The Opportunity process requires a consistent minimum set of information before the bid process begins. Currently, eight governance-critical validation rules differ in naming, messaging, and behaviour, which introduces user confusion, leads to overlapping or contradictory validations, and allows situations where mandatory information can be deleted or bypassed unintentionally.

This feature introduces a unified validation framework based on three governance cases with single naming logic, uniform error wording, and predictable validation behaviour across all affected fields. All validation rules display their error directly on the corresponding field to maximize clarity.

## User Stories
- As an **Opportunity Owner / Bid Manager**, I want mandatory information to be validated consistently during stage transitions and field edits so that governance-relevant data is always complete, reliable, and cannot be removed in non-permitted stages.

## Current Problems
1. Current logic does not distinguish between entering Bid Creation, Negotiation or Awarded and clearing information while already in these stages, reducing clarity and negatively affecting the user experience
2. The Expected Submission Date rule uses an amount threshold of 199,999 EUR, preventing correct validation for lower value opportunities and causing calculation upload errors
3. All rules except Bid Submission Date and Surveillance Director overlap with the Editable_Fields_if_Closed rule, leading to simultaneous errors when clearing fields after Closed Won
4. Both the Surveillance Director and the Expected Bid Submission Date can currently be deleted after an Opportunity is closed, although governance requires these fields to remain populated while still being editable

## Special Behavior: New Opportunity Creation
- Case 1 and Case 2 validation rules do NOT trigger when a user attempts to set the stage to "Bid Creation" or any later stage while creating a new Opportunity
- The existing creation stage warning (delivered with SFSUPPORTDE_BLM-8973) must be shown instead to prevent bypassing the early stage entry logic
- Any attempt to create an Opportunity directly in Bid Creation, Negotiation, Awarded, or Closed Won must show the existing creation stage warning

## Solution Design
- Implement three sets of validation rules:
  1. Require all eight fields before moving Opportunity to Bid Creation or later stages
  2. Prevent these fields from being cleared once the Opportunity is in Bid stages
  3. After Closed Won/Lost, allow edits but do not allow Surveillance Director and Project Margin to be blank
- Rename old rules with prefix `zdelete_` and deploy the new standardized rules with consistent error messages

## Acceptance Criteria
- [x] All eight fields relevant for the transition into Bid Creation and later stages - Nearshore / Offshore, Expected Contract Type, Bid Manager, Surveillance Director, Bid / No Bid Decision, Pre-Sales Risk Level, Expected Submission Date and Project Margin (%) - require a non-empty value when an Opportunity is moved from Prospecting or Qualification into Bid Creation, Negotiation, Awarded or Closed Won, as defined in the Case 1 table
- [x] None of the eight fields listed above can be cleared while the Opportunity is in Bid Creation, Negotiation or Awarded, although updates to existing values remain possible. This behaviour is implemented consistently for all fields as described in the Case 2 table
- [x] The fields Surveillance Director and Project Margin (%) cannot be cleared after an Opportunity has reached Closed Won or Closed Lost, while still allowing modifications to the existing values, as specified in the Case 3 table
- [x] All validation rules referenced in the Case 1, Case 2 and Case 3 tables use the exact English and German error messages defined in those tables and display the error at the respective field level
- [x] All validation rules use the naming conventions shown in the Case 1, Case 2 and Case 3 tables and follow the unified structure described in the story
- [x] The existing validation rules listed in the Additional Information section have been replaced, re-implemented or supplemented as required, and all replaced or reworked rules have been renamed using the prefix `zdelete_` for later removal
- [x] The amount threshold of 199,999 EUR for the Expected Submission Date validation has been fully removed so that validation behaviour aligns with the Case 1 and Case 2 definitions
- [x] When creating a new Opportunity and the user selects "Bid Creation" or any later stage, only the validation rule delivered with SFSUPPORTDE_BLM-8973 shall trigger while all validation rules introduced with this ticket (Cases 1–3) must remain suppressed during creation
- [x] No validation rule created or adapted as part of this story conflicts with other existing logic, in particular the rule Editable_Fields_if_Closed, and all fields behave consistently and predictably throughout the entire Opportunity lifecycle
